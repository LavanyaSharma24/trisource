3 · How it works — codes, algorithms & design

TriSource is a four-stage pipeline. Detection, correlation and scoring run client-side in vanilla JavaScript, so the logic is fully auditable and the tool runs offline from a file. Only .evtx parsing uses the optional Python backend.

Stage 1 — Parse (js/app.js → parseCSV · backend/evtx_parser.py)

Input is a CSV of host process events. The parser auto-detects the Timestamp, Image and CommandLine columns by header name and tokenises each row with a small quote-aware splitter, producing a normalised list of {ts, img, cmd} events. The demo case loads the project's real victim01 events instead of a file.

Real Windows logs: a Sysmon .evtx is posted to the optional Python backend (FastAPI + python-evtx), which decodes the binary log, keeps Sysmon Process Create records (Event ID 1) and returns {ts, image, commandline, record_id} — each event traceable to its original EventRecordID. Records it skips are counted, not hidden. Stages 2–4 then run in the browser exactly as for a CSV; the backend does no detection.

Stage 2 — Detect (js/rules.js → detect)

A signature engine runs every event against an ordered rule set. Each rule is a regular expression over the command line mapped to a MITRE ATT&CK technique and a severity:

{ "id": "T1053.005", "sev": "high", "pattern": "schtasks.*\\/create", "flags": "i",
  "rule": "Suspicious Command Patterns In Scheduled Task Creation" }

The rules live in rules.json, so they can be edited without touching code; the line under the input panel shows which rule set is active. Opened from disk, the page uses the identical copy embedded in js/rules.js (browsers block file:// reads).

Rules are ordered most-specific first, and the first match per event wins (O(events × rules)). This is the same matching model Sigma uses — a field condition yielding a technique and a level — which is exactly what Hayabusa and Chainsaw applied to the real Sysmon logs in the study. Caveats are attached where a real rule mis-labels a technique (T1112 → T1137) or where only threat-hunting rules catch it (T1057).

Stage 3 — Correlate (CASE_SOURCES join)

For the demo case, each detected technique is joined against the disk and memory findings — Prefetch (execution), Registry (persistence) and memory — recording for each source whether the technique was Y recovered, N not present, or – not applicable. These values are the real outputs of the project's three analysis tracks.

Stage 4 — Reconstruct & score (renderTimeline, renderMatrix)

Events are ordered into an attack timeline annotated with tactic and outcome (including failed techniques, e.g. wmic on Windows 11 25H2). Coverage is then scored: a technique counts as recovered when at least two independent sources contain it. Toggling a source recomputes the score live — demonstrating that removing any single source (e.g. an attacker clearing the logs) causes evidence to disappear.

Why it works

  • Technique-centric correlation. Mapping every artifact to an ATT&CK ID gives a common key to join otherwise unrelated sources (a log line, a prefetch file, a registry value).
  • Independence of sources. Because logs, disk and memory are captured and fail independently, agreement across two of them is strong corroboration — and disagreement is itself a finding (T1112 is invisible in the registry but visible in prefetch).
  • Severity triage. Reserving colour for danger (high severity and missing evidence) keeps the analyst's eye on the red flags instead of the noise.
